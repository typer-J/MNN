# 任务反思与经验沉淀

> **触发条件**：非平凡任务完成后，且存在可沉淀经验：debug、失败修复、反复试错、明显误判、流程缺口，或用户显式要求。
>
> **跳过条件**：简单执行、查询、格式调整、常规 CI 通过等没有新增教训的任务，无需执行此 skill。
>
> **服务对象**：所有 skill。本 skill 的产出是对其他 skill 文件的更新，不产生代码。

## 核心原则

### 🚨 对结果要有定力，不要自我欺骗

最大的风险是"觉得差不多了"的幻觉——结果不达标时，找外部原因搪塞然后降低要求宣布完成。

**常见的自我欺骗模式：**
- **功能任务**：输出不正确时归因于"量化精度不够"、"模型太小"、"这是预期的退化"，而不是继续排查实现 bug
- **性能任务**：优化没有效果时归因于"编译器已经优化得很好了"、"已经接近理论极限"，而不是继续尝试其他方案

**正确做法：**
- 测试目标在开始前就定好，不能中途降低标准
- 通过标准必须具体、可验证（"差不多能用"不算通过）
- 功能任务：人工验证不通过就是没通过，继续排查实现细节
- 性能任务：没有达到预期提升就继续优化，用数据证明已到极限而不是猜测

### TDD 思维：先定测试再写代码

每个子任务开始前明确三件事：
1. **通过标准是什么？** — 具体的预期输出
2. **怎么测？** — 可执行的测试命令
3. **什么不算通过？** — 明确列出容易自我欺骗的边界情况

文档综合与论文重构任务还必须先建立原文的完整“编号—标题—职责—证据边界”清单。相邻章节共享输入、成本模型或目标平台，不代表它们属于同一机制；任何合并、重命名或层级调整都必须能逐项映射回原文并显式说明依据。

以权威口径文档审计论文时，必须把发现分成直接矛盾、权威材料未支持的新增表述、可能误读的歧义和纯版式问题，并在逐句审阅前自动比较全部 `ref` 与 `label`。篇幅压缩应优先删除重复的边界声明、浮动表格和已由算法或图注表达的内容，同时保留证据范围、失败边界和实现权限等限定语；跨页或跨栏续句只有在语法或引用确实断裂时才算“断头句”。

论文段落压缩完成后必须重新扫描符号、限定词和术语：同一对象不能在框架段使用 \(T\)、在机制段改成 \(\mathcal{T}\)；`only`、`every`、`all` 等压缩时新增的量词要与相邻段落逐项核对；`probe`、`cache`、`memo` 等带实现含义的词还要回查是否与实验对象或部署路径混淆。不能因句子更短就沿用压缩前的口径验收结果。

冻结口径下的数值审计必须双向进行：既扫描权威文档明确废弃的旧数字，也要提取论文中的全部数字、样本计数和统计结论，反查它们是否已登记在权威结果表或后续 addendum。只存在于新图、派生脚本或未冻结汇总中的数值，即使看似合理，也只能标为未获授权的新增证据，不能默认进入正文。

用补充实验替换论文 TODO 时，不能只改占位文字；应先列出所有依赖该证据的表格行、证据类型、样本计数、相邻结论和限制段，再逐项同步更新。必须区分独立工作负载点、同一点的配对重复、完整候选组和单候选进程，不能用重复次数扩大泛化范围；正文数字还应同时回查机器可读汇总和原始产物完整性。

审计论文中的 “cache” 实现时，必须分别验证硬件数据 cache、实验日志归档、进程内静态锁存/资源复用和跨重启持久化映射，不能因变量名含 `cached` 或脚本保存了结果就认定 persistent cache 已实现。跨重启主张至少要找到 durable read/write、稳定 key、schema/版本与环境校验、失效/损坏回退、hit/miss dispatch 和 winner 应用路径；只在设计文档中出现这些字段仍属于 design-level evidence。TODO 中的 repack、内存和 service-ready 测量也应逐项审计，因为它们可独立于持久化实现存在。

复测异构平台元数据时，聚合式 `lscpu` 输出不能替代被测核心的拓扑证据：应归档逐 CPU cache 的 `shared_cpu_list`，并区分硬件频率上限、governor 配置和 workload 窗口内的逐次观测频率。动态采样必须覆盖完整 workload，保存退出码和采样耗尽标记；否则只能称为观测快照，不能作为受控实验状态。

论文框架图必须与正文的创新层级同构：创新机制、机制内子问题和跨候选合法性约束应使用不同的编号与视觉层级。交付前同时做术语残留扫描和论文栏宽内嵌渲染，确认旧层级没有重新出现在图注、标签或连线上，且缩放后的边栏文字仍完整可读。

当框架被限定为恰好 \(N\) 个机制时，验收应自动检查正文的机制小节数、图中的机制编号数和图注中的机制数都等于 \(N\)。合法性约束、初始化流程和执行时序只能作为机制内部段落或箭头语义，不能占用与机制平行的标题层级。

论文概览图默认用于表达关系，而不是承载正文论证：节点优先使用名词短语，把定义、适用条件和因果解释留在正文或图注。必须按最终栏宽检查信息密度；如果标签只能放大后阅读，就继续删减层级和说明文字。

## 执行流程

### 1. 识别教训

- 走了哪些弯路？错误假设是什么？
- 根因是什么？为什么没有第一时间找到？
- 方法论问题？跳步了？过早下结论了？把 bug 归因为外部原因了？

### 2. 判断归属

| 教训类型 | 更新位置 |
|---------|---------|
| 某个 skill 流程中的陷阱 | 该 skill 的 `common-pitfalls` 或步骤文件 |
| 通用工作方法论 | 该 skill 的 SKILL.md 顶层注意事项 |
| 跨 skill 通用经验 | memory 系统 |

### 3. 写入原则

- **只写方法论，不写单次任务的具体细节。** 可以附最小测试示例说明如何验证。
- **放在最显眼的位置。** 关键教训放 SKILL.md 顶部，不要埋在子文档末尾。
- **增加的同时审视现有内容。** 显而易见的、能从代码直接推出的指导删掉或精简。单个步骤文件不超过 500 行。
